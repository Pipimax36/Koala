# UI 重构 PR 拆分

关联需求：[Issue #1](https://github.com/Pipimax36/Koala/issues/1)。

本文件记录 Issue #1 的实现分组、代码边界和依赖；需求与验收以 [需求正文](./ui-refactor-issue.md) 为准。PR-0 等为计划编号，不是 GitHub 编号。各实现 PR 有实际改动后再创建，产品行为的未决项在对应实现前解决。

## PR 范围与验收

当前拆为 1 个文档基线 PR 和 8 个实现 PR；如果规则或运行状态改动超出一个可独立审查的功能，再按实际 diff 调整边界。PR-0 提交需求、原型、查看说明及本拆分文档；不修改生产界面。

### 建议分支与提交关系

- PR-0：`codex/ui-refactor-baseline` → `main`。
- PR-1：基于合入 PR-0 后的 `main`，分支 `codex/ui-shell`。
- 后续分支：`codex/ui-home`、`codex/ui-profiles`、`codex/ui-proxies`、`codex/ui-runtime`、`codex/ui-rules`、`codex/ui-core`、`codex/ui-settings`，均在对应依赖合并后从最新 `main` 创建。
- 不提前创建空 PR 或把需求文本当作页面实现提交。若需要并行且父 PR 尚未合并，使用明确的父分支作为比较基准，父 PR 合并后再调整目标分支。

### 每个 PR 的边界

- 每个页面 PR 同时交付界面、真实数据接入、失败状态、必要的行为验证及截图，合并后应用应可使用。不先合入生产环境中的模拟按钮，再把真实功能留给另一个 PR。
- 优先复用现有 hooks、store、IPC 和内核能力。若发现需要新增共享行为或修改协议，先提交一个有明确消费者的小型前置 PR，并更新依赖关系；不预先安排大规模主进程重写。
- PR-1 管公共框架；页面 PR 尽量只修改自身组件、翻译和必要的数据接口。公共组件变更说明受影响页面，并在该 PR 内回归，避免并行反复修改同一组件。
- PR-5 合并连接与日志是因为它们均属于运行数据查看。若实际 diff 或数据状态修改过大，可拆为两个同级 PR，验收范围保持完整。
- 各实现 PR 完成适用的 TypeScript、修改文件 lint 和构建检查；UI 改动附前后对比及关键异常状态截图；状态行为变化补充能覆盖成功、失败、恢复的验证。全部合并后再做一次跨页和目标平台总回归。
- 使用 `codex/` 前缀创建实现分支。优先从已合并的公共基线独立开分支；必须依赖未合并 PR 时，在描述中明确父 PR 和比较基准，避免将整个系列反复展示为一个 diff。
- 中间 PR 使用 `Refs #1` 关联本 issue，不使用会提前关闭总任务的 `Closes/Fixes`。若以后建立子 issue，各 PR 可关闭自己的子 issue；总任务在全部范围验收通过后再关闭。
